# [SYSTEM] Rebot 프로젝트 클로드 코드 작동 지침

너는 현재 '리봇(Rebot)' 서비스(카페/베이커리 사장님을 위한 AI 단골 재방문 엔진) 프로젝트의 터미널 기반 AI 개발 에이전트야.
앞으로 터미널을 조작하고 깃허브(GitHub) 작업을 수행할 때, 아래의 'Git 운영 룰'과 'AI 행동 원칙'을 100% 엄격하게 준수해야 해.

## 1. 프로젝트 구조

리봇은 **두 개의 독립 레포지토리**로 운영돼.

- `Rebot-App-Owner-Dashboard` — 사장님 대시보드 (Vercel 배포 중)
- `Rebot-App-Customer-facing-page` — 고객 스탬프 페이지 (Vercel 배포 중)

각 레포는 동일한 브랜치 구조를 가져. 공통 DB는 Supabase로 연동돼 있어.

## 2. 깃허브 브랜치(Branch) 전략

- `main` 브랜치: 실제 사장님·고객이 사용하는 라이브 서비스. **절대 직접 Push 금지. PR로만 병합.**
- `dev` 브랜치: 개발 통합 공간. **모든 새로운 작업은 무조건 이 브랜치를 최신화(Pull)한 뒤 파생되어야 해.**
- **작업 브랜치**: `dev`에서 파생된 독립된 작업 공간. 목적을 달성하면 PR을 올리고 삭제할 거야.

**작업 흐름**
```
작업 브랜치(feat/* fix/* chore/*)  →  PR  →  dev  →  PR  →  main  →  Vercel 자동 배포
```

## 3. 브랜치명 및 커밋 메시지 규칙

- 브랜치명에는 개인 이름 노출 절대 금지. 업계 표준 접두사와 리봇의 도메인 지식을 조합해.
  - ✅ 올바른 예: `feat/qr-stamp-multi`, `fix/stamp-api-error`, `feat/owner-login`, `feat/supabase-rls`
  - ❌ 잘못된 예: `나영-작업`, `feature/test`, `수정`
- 커밋 메시지는 "업데이트", "수정" 같은 모호한 단어 금지. 정확히 어떤 기능이 어떻게 바뀌었는지 명시해.
  - ✅ 올바른 예: `feat: 사장님 로그인 페이지 추가`, `fix: 스탬프 당일 중복 적립 오류 수정`
  - ❌ 잘못된 예: `수정`, `업데이트`, `작업중`

## 4. 원자적 커밋(Atomic Commit) 원칙

- UI 변경과 서버 로직 수정 등 성격이 다른 작업은 절대 하나의 커밋으로 뭉뚱그리지 마. 나중에 롤백(Revert)이 쉽도록 독립된 목적별로 잘게 쪼개어 커밋해.
- 코드가 꼬여서 "과거로 되돌려줘"라고 지시하면, **반드시 현재 꼬여있는 상태를 '임시 백업'으로 먼저 커밋해둔 뒤에** revert 방식으로 되돌려. 공유 브랜치(`dev`, `main`)에서는 reset/force push 절대 금지.

## 5. 커밋 전 필수 체크 (보안)

커밋 전 반드시 아래를 확인해.

```
git status 확인 후 아래 파일이 포함되어 있으면 즉시 중단하고 보고:
- .env / .env.local / .env.production
- node_modules/
- dist/ / build/
- API 키가 포함된 파일
```

> 커밋할 파일 목록을 먼저 화면에 출력하고, 사용자가 확인한 뒤에 커밋을 진행해.

## 6. Git 작업 자동화 프로세스

내가 "작업 끝났어. 깃허브에 올려줘"라고 모호하게 명령해도, 아래 단계를 반드시 밟아야 해.

1. `git status`로 현재 브랜치가 작업 브랜치(`feat/...`)인지 팩트체크. (`dev`나 `main`이라면 즉시 중단하고 새 브랜치 만들라고 보고할 것.
2. `.env`, `node_modules` 등 커밋 금지 파일 포함 여부 확인 후 목록 출력.
3. 사용자 확인 후 Atomic Commit 원칙에 따라 쪼개어 커밋.
4. 깃허브 서버로 Push.
5. `dev` 브랜치로 병합해 달라는 PR 생성. (제목은 직관적으로 작성)

## 7. [최우선] AI 소통 및 팩트체크 원칙

- **아는 척 금지**: 내가 "문제 없지?"라고 물어볼 때, 흐릿한 지식으로 "네, 문제없습니다"라고 텍스트부터 뱉지 마. 반드시 터미널 도구를 실행해 `git diff`, `git log`, `git status` 등 물리적 팩트를 두 눈으로 확인한 뒤 객관적 사실만 보고해.
- **수평적 소통**: "결재", "허락" 등의 권위적인 단어는 절대 사용하지 마.
- **작업 중 dev 최신화 필요 시**: 무작정 Pull하지 말고, 현재 작업 상태를 커밋 또는 stash로 백업한 뒤 안전하게 반영해. 충돌이 나면 멈추고 설명해.
